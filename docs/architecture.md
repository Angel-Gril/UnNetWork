# 架构与数据流

## URnetwork 的工作方式

URnetwork 是一个 **P2P 带宽市场**，不是传统的订阅制机场。

```
供给端：普通用户装客户端，贡献闲置带宽 → 获得使用他人带宽的额度
需求端：你消耗额度，流量从「某个贡献者的家宽」出去
```

这决定了它的全部特性：

| 特性 | 因为 |
|---|---|
| 出口 IP 是真实住宅 IP | 出口就是贡献者的家庭宽带 |
| 节点数量不稳定 | 贡献者随时上下线 |
| 延迟波动大 | 依赖对方的上行带宽和在线状态 |
| 出口 IP 会重复 | 同一贡献者被分配给多个请求 |
| 免费额度有限 | 用多少给多少，不付费就没有额外额度 |

## 代理的三种形态

每个"节点"实际是 URnetwork 开在入口服务器上的三个端口：

```
crisp.bringyour.com
  :7129  SOCKS5    ← 原生协议
  :7130  HTTP      ← 附加封装
  :7131  HTTPS     ← 附加封装 + TLS
```

端口号在同一个 block 内是连续的，但跨 block 不固定（7141-7174 之间的某一组）。

### 认证

统一是 HTTP Basic，`auth_token` 作用户名、密码留空：

```
Proxy-Authorization: Basic base64("<auth_token>:")
```

服务端对 `base64("TOKEN")` 和 `base64("TOKEN:")` 都接受，
但 `base64(":TOKEN")` 返回 407。

## 为什么是「扫描」而不是「签发」

### 签发模式的问题

`issue(key, country)` 会创建一个新的代理实例，占用一个槽位。
槽位满了就得删旧的：

```python
slots = list_slots(key)
if len(slots) >= 5:
    _req(key, "/network/remove-client", {"client_id": slots[-1]["client_id"]})
res = issue(key, country)   # 新签
```

**问题**：`slots[-1]` 是"列表最后一个"，不一定是本次签发的那个。
165 个任务下来，前面的产出被后面的任务删掉了。

实测结果：165 个槽位 → 只剩 60 个，产物里的节点全部失效。

### 扫描模式

`list_slots()` 返回的每个槽位已含完整连接信息：

```python
{
  "client_id": "01a1fe6d-...",
  "create_time": "2026-11-21T14:06:22Z",
  "proxy_client": {
    "proxy_host": "fireside.bringyour.com",
    "socks_proxy_port": 7165,
    "http_proxy_port": 7166,
    "https_proxy_port": 7167,
    "auth_token": "06GVSRFQR98L..."
  },
  "pro_features": ["socks_proxy"]
}
```

**直接读就能用**，不需要签发，也就没有可删的。

刷新耗时：10-23 分钟 → **1 分钟**。

## IP 去重的必要性

一次扫描的真实样本：

```
通过住宅校验: 81 个节点
唯一出口 IP:  19 个

23.246.184.30  出现 15 次   ← GoCodeIT，同一家供应商
23.246.184.33  出现 12 次
66.117.134.x   出现  8 次
...
```

**81 个"节点"实际只有 19 个出口**。不去重的话，策略组里塞满重复项，
用户切换节点时出口根本没变。

`--dedup-per-ip 3` 表示同一 IP 最多留 3 条，够用且能利用不同入口机房的延迟差异。

## 延迟为什么跳变

```
手机 ──①── bringyour 入口 ──②── 住宅 provider ──③── 目标
```

| 段 | 耗时 | 影响因素 |
|---|---|---|
| ① TCP + 认证 | 50-200ms | 你的网络到入口机房 |
| ② P2P 隧道（QUIC）| **1-13 秒** | 对方带宽 / 在线状态 / NAT 打洞 |
| ③ 普通请求 | 100-500ms | 目标站点 |

第 ② 段是瓶颈，而且是**不可控的**——你租的是陌生人电脑的一部分带宽。

同一节点连测 3 次的真实数据：

```
US-01  OK 13.7s | OK 1.1s | OK 1.4s
US-04  OK 13.7s | OK 2.1s | OK 1.0s
```

冷启动那次要 13 秒（打洞重试），之后就快了。这也是为什么：

- `probe` 超时要设 25 秒（否则误杀慢节点）
- 客户端 `url-test` 的 `timeout` 要设 10 秒（默认 5 秒太短）
- 节点名里带 `ms` 数字，但那只是探测时的耗时，不代表实际速度

## 设计取舍

| 决策 | 原因 |
|---|---|
| 默认 SOCKS5 | 冷启动 1 秒，http/https 要 5-15 秒会被测死 |
| `udp: false` | relay 是容器内网地址，外部不可达 |
| probe 超时 25s | 冷启动最长 15 秒，短了会误杀 |
| 并行 8 | 每 key 限速独立，8 个并发不互相影响 |
| 只复制无凭据文件到静态目录 | 含 `auth_token` 的配置只走鉴权通道 |
| 节点名 `CC-NN-msms-IP` | 满足 mihomo 模板的 `\bCC\b` 词边界 |
